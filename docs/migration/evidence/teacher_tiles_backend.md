# Teacher/admin mobile tiles: Flutter endpoint -> backend verification

Read-only audit, no DB. Generated 2026-10-07. Repos: ERP = D:/next_lms_erp, Flutter = D:/new_mobile_lms_k12.
Anything that depends on DB rows (teacher_mobile_homescreen.sub_title_api, mobile_dynamic_page, mobile_pages, tblmenumaster.link rights) is marked "DB-dependent / not verified".

## 0. How the Flutter app calls everything (applies to every row)

- Tile routing: `lib/screens/screen_registry.dart:29-72`. Order: ported screen by `screen_name` (teacher -> `teacherScreens`, admin/other staff -> `adminScreens` then `teacherScreens`; `lib/screens/teacher/teacher_screens.dart:18-64`, `lib/screens/admin/admin_screens.dart:17-37`), then `render_type=webview` + `/mobile/custom/<slug>` -> native Page Builder screen (`lib/core/native_target.dart:34-42`), then `native_dynamic` -> DynamicPageScreen, then any tile with non-empty `sub_title_api` -> generic DataScreen that does `LegacyApi.post(item.api)` (`screen_registry.dart:60-69`), else "not available yet".
- `sub_title_api_param` is parsed (`lib/core/feed.dart:34`) but never sent anywhere (grep `apiParam` in lib/: only feed.dart and two dummy FeedItems). So a DB tile that relies on an api_param such as `action=payslip` cannot work through the generic DataScreen.
- Menu: `POST /teacher_homescreen` (`lib/core/feed.dart:91-100`) -> TA:19 -> `teacherapiController::teacher_homescreen` (TC:195-287). ACT-checked, but profile id/name/tenant are read from the BODY (TC:204-206, 221-227), so a valid token can request another role's/tenant's menu. The newer `GET /api/mobile/bootstrap` (api.php:100, `api.session`, identity from token) is not used by this Flutter app.
- Transport for ported screens: `LegacyApi` (`lib/core/legacy_api.dart:58-77`): multipart POST (or GET with query), header `Authorization: Bearer <token>`, plus fields from `identity` (`legacy_api.dart:32-43`): `token, sub_institute_id, syear(mobile_syear), user_id, teacher_id, admin_id, student_id (all = login id), user_profile_id, user_profile_name, type=API`. Base URL default `https://dev.triz.co.in` (`lib/core/config.dart:10-13`).
- Token: `POST /api/api-login` (`lib/core/auth_controller.dart:65`) -> `ApiLoginController::login` (app/Http/Controllers/api/ApiLoginController.php:417-434) payload = `{id, sub_institute_id, is_admin, client_id, user_profile_id, is_student}` (+ iat/exp only if env JWT_TTL_MINUTES>0, :428-432; default = never expires). No `teacher_id` claim.

Backend abbreviations: TA = routes/teacherapi.php, AA = routes/adminapi.php, ST = routes/student.php, WEB = routes/web.php, HR = routes/hrms.php, TC = app/Http/Controllers/api/teacherapiController.php, AC = app/Http/Controllers/api/adminapiController.php.

Auth classes used below:
- **ACT** = `resolveActingTeacherId` (TC:56-106): validates JWT signature, decodes payload from the `Authorization` header only (TC:66-73; a client that sends only body `token` gets 403 "Token context could not be resolved"), loads tbluser (status=1, same tenant as token) INNER JOIN tbluserprofilemaster (TC:82-88). Non-admin -> acting id is forced to token `id`; admin profile (is_admin 1/2, profile parent_id 1, or name Super Admin/Admin/School Admin, TC:112-125) -> body `teacher_id`, then `created_by`, then `user_id` is honoured. Flutter sends teacher_id = own id, so both work. Tenant is NOT compared with body `sub_institute_id`.
- **JWT-only** = controller does `jwtToken()->validate()` (signature only; ids and tenant come from the body).
- **SESS** = route has middleware `session`: `SessionMiddleware` (app/Http/Middleware/SessionMiddleware.php:20-33) hydrates a session from the verified JWT when body/query `type` is API/JSON (Flutter always sends it via identity). Tenant/user in the session are then token-derived (`HydratesLegacyApiSession.php:60-130`). Controllers may still read the body instead (noted per row).
- Route files teacherapi.php and adminapi.php are mounted with NO prefix and NO middleware group (RouteServiceProvider.php:391-400). URLs are `/get_adminStudentList` etc., not `/api/...`; no CSRF, no throttle, and `RequireApiJwt` (`api.jwt`, config/api_guard.php) never applies because it only matches paths starting `api/` (RequireApiJwt.php:107-112).
- student.php / web.php / hrms.php / result.php / cal.php are `web` group: CSRF applies. `VerifyCsrfToken::$except` (VerifyCsrfToken.php:20-26) only covers `circular/*`, `api/*`, `fees/*` and the full URLs of erp.triz.co.in, dev.triz.co.in, 127.0.0.1:8000. On any other host these legacy POSTs return 419 (also in docs/api-migration-staff.md risk 3).

## 2. Does an /api/api-login token work?

Yes for all of the above that validate a JWT: payload keys are `id, sub_institute_id, is_admin, client_id, user_profile_id, is_student` (ApiLoginController.php:417-424). `resolveActingTeacherId` needs only `id` + `sub_institute_id` (TC:75-76) and the tbluser/profile rows; it does not need `teacher_id`. Gotchas:
- It reads the payload from the `Authorization: Bearer` header only (TC:66-73). Flutter sends both header and body `token`, so fine; a client that sends only body `token` passes `validate()` but gets 403.
- It does not look at `is_student`: a student token's `id` is a tblstudent.id, yet TC:82-88 looks it up in tbluser (same tenant) and would act as the staff user with the same numeric id.
- Inner join to tbluserprofilemaster: a user whose profile row is missing gets 403 "Active user context was not found."
- Other controllers (adminapi, student.php legacy, easy_com legacy, visitor, hrms_api.php) only verify the signature; tenant and user id are whatever the body says.
- `api.jwt` (RequireApiJwt, the V1 guard) enforces "body school == token school" only for `api/*` paths listed in config/api_guard.php (`academic-terms`, `get-*`, admission, lms-*, etc.). None of the teacherapi/adminapi/student.php endpoints are covered because they are not under `/api/`.

## 3. Caveats (cross-cutting, ranked)

1. `GET /lms_data` (WEB:638, AJAXController.php:2985-3071) is a public, unauthenticated arbitrary-table reader (`table`, `filters`, `all_tables=1`, `table_data=1`). Flutter depends on it for t_my_attendance, leave types/history fallbacks and the marks term fallback. Anyone can read tbluser/tblstudent etc. Replace the Flutter callers with `/api/hrms/attendance`, `/api/leave/options`, `/api/academic-terms`, then protect/remove the route.
2. Public/unauthenticated writes: `/add_visitorAPI` (JWT check commented out, triggers SMS), `/fees/get_online_receipt` (token = encrypted student id only), `/studentFeesDetailAPI` controller (JWT block commented out, only route middleware stops it), `/hrms/myleave/{id}` (fake data, no auth).
3. Tenant/identity trusted from the body on almost every legacy endpoint (adminapi, student.php `*API`, visitor, easy_com legacy, co-scholastic store, leave-authorisation store, calendar fetch with no tenant filter). With one valid token a caller can read/write another school's students, parents' mobile numbers, leave decisions, fees. Only teacherapiController applies ACT (and it also does not compare the body tenant with the token tenant).
4. Role checks: adminapi endpoints, easy_com send/reports, `/api/leave/requests`, student-care discipline have no staff/role check; a student/parent token works.
5. Parameter/field mismatches that make a Flutter feature fail against this backend: admin parent-comm reply (`parent_comm_id` vs `parent_communication_id`), exam-schedule upload (`attachment` vs `filename`), visitor photo (`file_name` vs `visitor_photo`), my-attendance month filter, teacher requisition list (SQL error `u.status` on alias `tu`, TC:1629), teacher gallery list (endpoint intentionally returns no data), admin fees collect (401 Unauthenticated because no `type=API`), teacher task list (inner join on approved_by), admin complaint list (inner join on solver).
6. Validation failures answer HTTP 200 with a `response` object and no `status` in most TA/AA methods; Flutter `LegacyApi.ok` (legacy_api.dart:119-125) counts any body with a non-message key as success, so these show a false "saved".
7. Uploads: no size or mime validation anywhere (`image`, `attachment`, `attachment[]`, `stu_image[]`, `image[]`, `filename`, `file_name`); several store to disk with second-resolution names (collision risk); content/exam-schedule go to the digitalocean disk but are read back via `/storage/...` URLs.
8. Capture attendance has no recognition/AI backend in this repo's adminapi (see row); the screen can only fall back to manual roster marking.
9. `public/hrms_api.php` (tiles t_hrms/t_payroll/t_salary_slip candidate): hard-coded database root credentials in a web-served file plus SQL injection; rotate those credentials and remove or rewrite the file. Note a second stale copy at `public/public/hrms_api.php`.
10. `teacher_homescreen` returns a menu for whatever profile/tenant the body claims (TC:204-227); prefer `/api/mobile/bootstrap`.
11. CSRF: every web-group legacy POST (student.php, web.php, hrms.php, result.php, cal.php) returns 419 on hosts outside the VerifyCsrfToken whitelist (VerifyCsrfToken.php:20-26); teacherapi/adminapi/easy_com/`api/*` are exempt.
12. Not verified (needs DB): which of these tiles have a non-empty `sub_title_api`, the exact `sub_title_api_param`, the 9 webview slugs, mobile_dynamic_page rows, tblmenumaster.link values that decide whether `check_permissions` actually enforces rights on routes such as `save_student_attendance`, `student_homework.store`, `hrms_in_time.store`.
